# revu:report

ローカルに蓄積されたレビュー結果（`~/.revu/{owner}/{repo}/pr-{N}/...`）を横断的に読み、**繰り返し現れる同種の失敗パターン**を抽出・グルーピングして、傾向レポートを**チャットの返答として**出力する（TUI での表示は将来の拡張。ファイルは書かない読み取り専用の skill）。

## 入力

```
/revu:report [<owner>/<repo> ...] [--profile <name>] [--all]
```

- 引数なし: cwd のリポジトリのレビューを対象
- `<owner>/<repo> ...`: 指定リポジトリ（複数可）を横断
- `--profile <name>`: 指定プロファイルに属するリポジトリ群を横断（active でないプロファイルも指定可）
- `--all`: プロファイルに関係なく、登録済みリポジトリ**全件**を横断

## 手順

### 1. 対象リポジトリの決定

- 引数なしの場合: `revu validate` を実行し、`OK` 行のパスから `~/.revu/{owner}/{repo}` を base として得る（cwd 非依存で指定したい場合は slug / `--profile` 指定を促す）
- `--profile <name>` の場合: 対象 slug 群を取得する:

```bash
revu repo list --profile <name>
```

  未宣言のプロファイル名はこのコマンドがエラーにするので、`revu profile list` の一覧を添えて聞き直す
- `--all` の場合: active プロファイルを無視して登録全件を取得する:

```bash
revu repo list --all
```

- slug 直接指定の場合はそのまま使う。いずれの場合も base は `~/.revu/<owner>/<repo>`。ローカルレビューが無いリポジトリはスキップして母数の注記に含め、レポートの「対象:」にはどの指定（cwd / profile 名 / all / slug 列挙）だったかを明記する

### 2. レビューの列挙と読み込み

各 base について:

```bash
ls <base>
```

- `pr-*` ディレクトリを列挙し、各 PR の**最新の SHA サブディレクトリ**（`review.yml` を含む、複数あれば最も新しいもの）を対象とする。同一 PR の旧世代は数えない
- 各対象の `review.yml` を `Read` し、`comments[]` のメタ（id / severity / category / path / line / status）と `body_file` を得る
- 各コメント本文（`comments/*.md`）を `Read` する。見出し `## [severity] タイトル` と本文が分類の主材料
- 現在の severity 設定と不整合な古いレビューも対象に含める（`revu validate` は通らなくても Read はできる。severity 名は当時の記載のまま扱う）
- 母数（リポジトリ数・PR 数・コメント数）を控える

### 3. 似た失敗のグルーピング

コメントを**意味的に**クラスタリングする。判断材料と規約:

- 主材料: 見出しと本文の内容（何を間違えたか・何が欠けていたか）。補助材料: `category`、`path` の拡張子・ディレクトリ、code suggestion の内容
- 「同じ根本原因・同じ種類のミス」を 1 パターンとする（例: 「ハードコード文字列の i18n 未対応」「入力バリデーション欠落」「エラーハンドリングの握りつぶし」「N+1 クエリ」）。category が同じでも原因が違えば別パターン、category が違っても原因が同じなら同パターン
- **2 件以上**現れたものを「繰り返しパターン」として扱い、1 件だけのものは「単発の指摘」にまとめる
- パターン名は日本語で、原因が一目で分かる命名にする（category 名の言い換えにしない）

### 4. レポートの出力（チャット）

以下の構成で出力する:

```
# レビュー傾向レポート

対象: {リポジトリ一覧} / PR {M} 件 / コメント {N} 件（{期間: 最古〜最新の generated_at}）

## 繰り返し現れる失敗パターン（件数順）

### 1. {パターン名} — {件数}件
- 出現: {repo#PR (comment id)} の一覧
- severity: {内訳}   status: accepted {a} / rejected {r} / pending {p}
- 内容: パターンの説明（何がどう失敗しているか）
- 代表例: 「{見出しの引用}」({repo}#{PR} {path}:{line})
- 対策の示唆: 再発防止に効きそうな仕組み・規約・レビュー観点

### 2. ...

## 単発の指摘
- {見出し} ({repo}#{PR}) の簡潔な列挙

## 総括
- 全体傾向（どの領域・カテゴリに失敗が偏っているか）
- rejected が多いパターンがあれば「レビュー側の誤検出傾向」として区別して指摘
- 頻出パターンを `.revu/guidelines/`（config の [review] guidelines）へ観点として追記する提案（該当する場合）
```

- 件数・出現箇所は必ず実データに基づける（水増し・推測をしない）
- `rejected` のコメントは「コードの失敗」ではなく「レビューの誤検出」の可能性があるため、パターン集計に含めつつ status 内訳で判別できるようにする
- コメントが 0 件（サマリのみのレビュー等）の場合はその旨を報告して終了する

## 注意事項

- **ファイルを書かない・変更しない**（レポートはチャット出力のみ。保存を求められたら Write で任意の場所に書き出してよい）
- 対象が多くコンテキストに乗り切らない場合は、リポジトリ単位で分割して読み、パターン集計を逐次マージする（全件を読んだうえで集計すること。読めなかった分があるなら母数に明記する）
- 個別レビューの閲覧は `revu:read`、編集は `revu:edit`、削除は `revu:delete` に切り替える
